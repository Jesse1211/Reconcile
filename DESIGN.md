# Reconcile — DESIGN.md

> A daily self-motivation / "reconciliation" iOS app. Each day the user reconciles with
> themselves: morning motivation (Quote) → daytime focus (stopwatch Timer) → evening
> verification (MIT). Pure-local SwiftData, one online read-only call (ZenQuotes).

This document is the **locked decision ledger** for the hands-off build. Build agents cite
ADRs; they do not re-litigate decisions. Anything undecided is an OQ.

---

## 1. Product summary

- **Actor**: single individual user. No account, no multi-user, no permissions layer.
- **Daily loop**: open → today's Quote → set/view today's MITs → focus with stopwatch → verify MITs (done/not-done).
- **Core entity**: **MIT** (Most Important Task) — set in the morning, verified at night, same single thing with a full lifecycle.
- **Storage**: pure local **SwiftData**. The only network call is a read-only fetch from **ZenQuotes**.

---

## 2. Domain model

- **Bounded Context**: `Reconcile` (single).
- **Aggregate roots**:
  - **MIT** — Entity. Stable identity, mutable content. The reconciliation core.
  - **Quote** — Entity. user-entered / api-liked unified into one persisted type; identity needed for like-dedup. The library starts EMPTY — no bundled content.
  - **FocusSession** — Entity. Stopwatch (count-up from 0). Standalone (not tied to MIT). Timestamp-based.
  - **DailyFeeling** — Entity. The daily diary/mood entry. Exactly one per local calendar day. Holds mood (0-5), stress (0-5), and an optional free-text "why".
- **Value objects**: `QuoteSource {user, api}`, `MITStatus {open, completed}`, `TodayScope {mine, online}`, `MoodScale (0...5)`, `StressScale (0...5)`, timestamps, durations.
- **Invariants**:
  - **INV-1** MIT timeline monotonic: `createdOn <= completedOn`.
  - **INV-2** Only `open` MITs roll to the next day; `completed` is terminal (flippable same-day, locked cross-day).
  - **INV-3** A cross-day historical MIT is read-only (content & status).
  - **INV-4** A liked API quote is deduped by a pinned `dedupKey`: `dedupKey = normalize(text) + "|" + normalizeAuthor(author)`, where `normalize(text)` = the text lowercased, trimmed of leading/trailing whitespace, with **internal runs of whitespace collapsed to a single space**, **curly/smart quotes and apostrophes normalized to their straight ASCII equivalents** (`“ ” → "`, `‘ ’ → '`), and a **single trailing period stripped**; and `normalizeAuthor(author)` maps `nil`, empty string, and `"Anonymous"` all to the same empty/`"anonymous"` value. Same text — regardless of how the author is written (nil vs "" vs "Anonymous") — dedupes to one stored row. **Intent:** the same quote fetched twice (or entered twice, or entered by the user and later fetched from ZenQuotes) must produce the SAME `dedupKey` and dedupe to one row — the text-normalization rules (whitespace collapse, curly→straight quotes, trailing period) exist precisely so an api-vs-user or fetched-twice duplicate collapses across curly-vs-straight quotes, doubled spaces, and a trailing period.
  - **INV-5** FocusSession duration is timestamp-derived and never negative.
  - **INV-6** Soft-deleted MIT is excluded from all stats but retained in the DB.
  - **INV-7** At most one `DailyFeeling` per local calendar day (writing again the same day updates it, not inserts). Mood & stress are each within `0...5`; the "why" text is optional.
  - **INV-8** A cross-day historical `DailyFeeling` is read-only (same lock rule as MIT, INV-3).
  - **INV-9** A `Quote`'s liked-ness has exactly ONE stored representation: `likedAt?` (a timestamp). `liked` is a derived/computed property with `liked ⇔ likedAt != nil` — never a second stored field. **Quote hard-delete is `source`-dependent (ADR-035, refined by ADR-039):** for a `source == api` row, un-saving (un-liking) and deleting are THE SAME action — the row is **REMOVED** from the DB (there is NO "retain with `likedAt = nil`" state for an api row). For a `source == user` row, the row IS the user's authored content: un-liking it (clearing `likedAt`) **must NOT delete it** — the row persists (with `likedAt = nil`) because `source == user` keeps it in the `mine` pool regardless; a user row is removed ONLY by an explicit "delete my quote" action. So the "retain with `likedAt = nil`" state exists **for user rows only** (ADR-039 carve-out) and never for api rows — this does not contradict the api-row hard-delete rule. There is no soft-delete/trash for quotes (unlike MIT's ADR-008).
- **MIT lifecycle**: `created(open) → [daily roll while open] → completed`; `→ soft-deleted` from any non-terminal state.
- **Cross-aggregate refs**: none in first release.
- **Widget shared snapshot is a read-only projection (not an aggregate).** The WidgetKit extension (ADR-041–ADR-045) does NOT read the SwiftData store directly; it reads a small **shared snapshot** the app writes into an App Group container (today's-quote text+author, the running-session `startedAt` OR today's accumulated focus seconds, and the persisted `Theme`). This snapshot is a **read-only projection** of the app's state — the app's SwiftData store stays the single source of truth; the snapshot is NEVER authoritative, never written by the widget, and adds no new aggregate root or invariant. It is a derived view rebuilt from the store whenever the relevant state changes (ADR-042).

## 3. ADR ledger (locked decisions)

- **ADR-001 — Pure-local SwiftData persistence.** All data (MIT, Quote, FocusSession) lives in local SwiftData. No account/backend. *Rationale: privacy, offline, fastest first release.* iCloud sync deferred (OQ-01).
- **ADR-002 — MIT is the core aggregate, named `MIT` in code and UI.** Ubiquitous language: code == business vocabulary. *Rationale: user speaks "MIT"; no translation layer.*
- **ADR-003 — Multiple MITs per day, no upper limit.** *Rationale: user decision; focus is preserved by the "most important" framing, not a hard cap.*
- **ADR-004 — MIT content & verification are freely mutable on the current local day; locked cross-day.** open↔completed flippable same-day; content editable same-day. After the local calendar day rolls, the historical record is read-only. **Completion field bookkeeping (D1):** completing sets `status = completed` AND `completedOn = today`; flipping `completed → open` the SAME day sets `status = open` AND `completedOn = nil` (so the daily-completed-count, which counts by `completedOn` per ADR-006, stays correct and does not over-count a re-opened MIT). *Enforces INV-2, INV-3.*
- **ADR-005 — Uncompleted MITs auto-roll to the next day; completed ones do not.** Rollover is the same record advancing its "appears-on" day, NOT a per-day copy. Triggered at the **device local calendar day** boundary, computed **lazily on app open** (no background task). No cap on days rolled. **App-open sequence & lock ordering (D2):** on app open the steps run in THIS order — **(1) rollover FIRST:** advance `appearsOn = today` for EVERY MIT with `status == open AND !isDeleted AND appearsOn < today`; **(2) THEN apply the cross-day read-only lock** (INV-3/ADR-004) ONLY to records that are terminal (`completed` or soft-deleted) OR still historical (`appearsOn < today`) AFTER step 1. Because step 1 runs first, an `open`, non-deleted, past-due MIT is ADVANCED to today (and thus editable) — it is NEVER frozen by the lock. *Enforces INV-2, INV-3. Uses calendar-day arithmetic so DST is correct; does not correct backward clock changes.*
- **ADR-006 — No completion rate, no streak. The only stat is count of MITs completed per day.** A completed MIT counts toward its **completedOn** day. *Rationale: user decision; keeps stats honest and simple under rollover.*
- **ADR-007 — A single Summary screen aggregates all stored data by calendar day.** MIT completion data and focus-time data are shown together on one Summary screen, aggregated per local calendar day. Includes a per-MIT lifecycle timeline (an MIT's span from created-day to completed-day, showing how many days it rolled). **Delete-gap rendering:** the timeline spans `createdOn` → `completedOn` (or → today if still open); a period during which the MIT was soft-deleted (between `deletedAt` and a later cross-midnight restore, ADR-030) is shown as a GAP / muted segment — NOT as continuous rolling — so the timeline is honest about the deleted stretch rather than implying the MIT rolled uninterrupted. *Rationale: user decision; "每日 MIT 和每日工作时间存在一起 … 通过 graph 展示".*
- **ADR-017 — Summary screen content & charts (Swift Charts).** The Summary screen shows: (1) **daily completed-MIT count** as a bar/line chart; (2) **daily total focus duration** as a bar/line chart; (3) the **per-MIT lifecycle timeline** (list/gantt, not a chart); (4) **summary KPI cards** (total completed MITs, total focus time, current open/rolling count). The **"current open/rolling count" KPI predicate** = count of MITs where `status == open AND isDeleted == false` (regardless of `appearsOn`). Today's rolled-in list length and this KPI MUST derive from the SAME query (read-model consistency, T10). Time range is **switchable Week / Month / All** (ADR-006 defines the MIT count; ADR-014 the focus duration). FocusSession stays a standalone aggregate (NOT bound to a specific MIT) — the join is by calendar day only. **"Total focus time" KPI == sum of split chart bars (ADR-032):** the total-focus-time KPI over a range is the sum of the SAME split day-portions the focus-duration chart uses (so KPI == Σ chart bars within the range), with the range filter applied **per split-portion** — a range-boundary-spanning session counts only its **in-range** portion. *Rationale: user decision.*
- **ADR-019 — Evening reconciliation includes a DailyFeeling diary entry.** As part of the evening verify step, the user can record one diary entry per day: first pick a **mood** (0-5 scale) and a **stress** (0-5 scale), then write a free-text "why". *Rationale: user decision "feeling 用于让用户写日记 … 先选一个 0-5 的心情/压力 scale，然后讲为什么".*
- **ADR-020 — DailyFeeling is one-per-day; mood & stress required, "why" optional; same-day editable, cross-day locked.** Exactly one entry per local calendar day (re-saving updates it, INV-7). Both 0-5 scales are required to save; the text is optional. Editable within the current day, read-only after the day rolls (INV-8, mirrors ADR-004). *Rationale: diary semantics = "today's mood".*
- **ADR-021 — DailyFeeling capture semantics.** ~~Store-only in first release.~~ **SUPERSEDED by ADR-023** for the display aspect: DailyFeeling is captured in the evening reconcile step (one-per-day, same-day editable, cross-day locked) AND its mood/stress trend is now shown on Summary (ADR-023). The capture/storage rules (INV-7/-8) are unchanged.
- **ADR-022 — Two switchable visual themes: "Ledger" and "Day Arc".** The app ships with two full themes the user can switch in settings. **Ledger**: paper/ink neutrals, serif + mono, ruled columns, tabular figures, a single ledger-red accent for rolled-over ("carried") items and a running balance. **Day Arc**: a time-of-day gradient ground (dawn on Today, midday on Timer, dusk on Summary), a vertical time-spine, glass cards. Both must support light & dark. The chosen theme is persisted. *Rationale: user decision "这两个我都要 … 给这个项目加了一个 theme".* Implementation: a `Theme` enum + a token/`Environment`-driven styling layer so screens are theme-agnostic and read tokens (color, type role, surface) from the active theme — screens are authored once, themed twice.
- **ADR-023 — Summary surfaces mood & stress trends (promotes OQ-07 into first release).** The Summary screen includes a mood/stress trend chart (and an average-mood KPI) over the selected Week/Month/All range, drawn from DailyFeeling. This supersedes the store-only limitation of ADR-021 for the *display* aspect (DailyFeeling is still one-per-day, same-day editable, cross-day locked — INV-7/-8 unchanged). *Rationale: user decision "提到首发（上图表）". The supersession of ADR-021's store-only clause is stated once, above.*
- **ADR-024 — Creating a MIT is a full-screen "intention ritual", entered from a placeholder row (not a floating FAB).** Today's MIT list ends in a dashed placeholder row ("Set today's most important…" / an empty spine node). Tapping it pushes up a full-screen, low-chrome intention screen: a guiding eyebrow, the date, a large serif text input for the one thing, and an **optional collapsible "why does it matter today?" (reason)** field. Each theme dresses it (Ledger: paper + date masthead + hairline, "Record entry"; Day Arc: dawn gradient, "Begin where the light is", "Set it"). Save creates the MIT (days=1) with the optional reason, dismisses, toasts with undo. *Rationale: user decision — the plain FAB+single-line sheet felt generic and lacked ritual; setting the day's most important thing should feel deliberate.*
- **ADR-025 — Quote has a manual refresh that swaps within the currently selected source pool.** A ↻ control on the daily quote fetches a different quote *from the active `TodayScope`*: if the scope is `online` it requests a DIFFERENT quote from ZenQuotes via **`/random`** (NOT `/today`, which is deterministic per day and would return the same quote — loading state; on failure follow ADR-013, `online` shows error+retry); if the scope is `mine` it picks a random different quote from the local `mine` pool (excluding the current one). Refresh manually overrides the day's deterministic pick and persists as the (day, scope) override (ADR-026); it does not change tomorrow's pick. *Rationale: user decision — a refresh must produce a genuinely different quote, so `online` refresh uses `/random`.*
- **ADR-018 — Quote storage is unified.** Liked API quotes and user-entered custom quotes are stored together in the one `Quote` table (distinguished by `QuoteSource {user, api}`). There is no bundled content; the table starts empty and is fed only by user entry + api-likes. *Rationale: user decision "saved API / custom quote 都会存储在一起"; this is the concrete storage statement behind ADR-009/-010.*
- **ADR-008 — MIT delete is a soft delete.** Removed from lists, retained in DB flagged deleted, excluded from all stats (INV-6). Undo via short-window snackbar. *Rationale: mis-tap safety; history integrity.*
- **ADR-009 — Two quote sources, both first-release: user-entered and api-liked — unified into one `Quote` type.** `QuoteSource {user, api}` distinguishes origin. There is NO built-in quote library; the personal library starts EMPTY and is populated only by manual entry and by liking (persisting) an API quote. *Rationale: owner decision — no bundled content.*
- **ADR-010 — Liking = persisting an api-fetched transient quote into the local DB.** An API quote fetched for display is transient (not yet in the library); liking it PERSISTS it as a local `Quote` row (`source == api`, `likedAt` set) so it is offline forever. **User-entered quotes need no separate like** — they go straight into the library on entry (they are inherently "saved"). Like is available BOTH from the Library screen AND directly on today's quote (a ♡/♥ toggle next to refresh on the Today screen) — same persistence path. Liking is deduped by the pinned `dedupKey` formula (INV-4): liking an API quote whose `dedupKey` already matches a persisted row (e.g. a user-entered duplicate) sets `likedAt` on that EXISTING row rather than inserting a second one. **Un-like is `source`-dependent (ADR-039 carve-out):** un-saving (un-liking) an **`source == api`** row is a HARD delete — it REMOVES the row (ADR-035/INV-9), same action as delete, with no "retain with `likedAt = nil`" state. But if the matching persisted row is **`source == user`** (a user-authored quote that was ALSO liked, e.g. the like landed on a user duplicate), un-liking it merely clears `likedAt` and **RETAINS the row** — it is the user's authored content and stays in the `mine` pool via `source == user`; it is removed only by an explicit "delete my quote" action. *Rationale: owner decision — liking is the persist path for transient online quotes; there is no builtin to like; un-liking must never destroy user-authored content.*
- **ADR-011 — Quote source is user-selectable per `TodayScope` (exactly two sources: `mine` / `online`).** The daily displayed quote is chosen deterministically per the selected scope for the local day. There is **no mixed/union scope** — a scope is EITHER the user's local library OR the single online quote, never both. A manual override — the `DailySelectedQuote` record for (day, scope), ADR-026 — takes **precedence** over the derived pick when present.
  **`mine` pool predicate (owner decision):** `mine` = quotes where `source == user OR liked == true` — i.e. everything in the local library that is user-authored or liked (with no builtin, this is effectively the whole persisted library, since api rows only exist once liked). The `mine` pick is derived **entirely locally** by seeding an index into the local `mine` pool **stably sorted** (e.g. by `dedupKey`) — seed = **(day, scope)** — so the pick is **stable under pool growth**: adding quotes that sort after the picked one does not change today's derived pick for that (day, scope).
  **`online`** = the single ZenQuotes online quote only (no local content).
  **Pick composition per scope (precise):**
  - `mine`: pick = the **local** deterministic index into the local `mine` pool via `pick()`. If that pool is **EMPTY → nil** (guiding empty state, ADR-033/ADR-034); if **size 1 → that quote** (no modulo-by-zero).
  - `online`: pick = the **`/today`** online quote (deterministic per calendar day; no local indexing). Offline → ADR-013 error + retry. `mine` never fetches.
  **`pick()` local function contract (|pool| ∈ {0,1}):** the local pick function (used by `mine`) returns `Quote?` — **`nil` when the local pool is empty** (caller renders the guiding empty-state per ADR-033/ADR-034; NO modulo-by-zero), and **the sole element when size 1**. *Rationale: owner decision — collapse the three-state scope to two clean sources (local library vs one online quote); `online` is picked directly (not indexed), removing the incoherence of indexing one live online quote in a `dedupKey` sort. `/random` is used only for browse-to-like in the Library (T8/ADR-012) and for `online`-scope refresh (ADR-025/ADR-012).*
- **ADR-012 — Online quotes come from ZenQuotes (no API key).** Read-only. **`/today` is the DEFAULT daily online quote source** (deterministic per calendar day — the online pick in the `online` scope, ADR-011); **`/random` is used for browse-to-like in the Library (T8) AND for a manual refresh in the `online` scope (ADR-025/ADR-026).** This binding is pinned: the DEFAULT daily online pick uses `/today` and never `/random`; a manual refresh-override in `online` uses `/random` (so the refreshed quote actually differs — `/today` is deterministic and would not change), and browse-to-like uses `/random`, never `/today`. *Rationale: no key management, has a daily endpoint; `/today` gives a stable default, `/random` gives a genuinely different quote on demand.*
- **ADR-013 — Online failure handling.** Scope=`online` + no network/API failure → **show error + retry button** (no silent fallback; `online` has no local content to degrade to). Scope=`mine` NEVER fetches, so it has no online failure mode. Single request timeout ~10s; manual retry; no aggressive auto-retry; no content moderation. Same-day API result cached (no repeat request that day). **The same-day cache is a TRANSIENT in-memory cache** — the fetched/displayed online quote is held only in memory for the day; it is NOT a persisted `Quote` row. Displaying or refreshing the daily online quote NEVER creates a `Quote` row (the library-persist path is a user ♡ like only, ADR-010/ADR-034). *Enforces SF-A/SF-B.*
- **ADR-014 — FocusSession is a standalone stopwatch.** Count-up from 0, stop anytime. Multiple sessions/day allowed, each independent. Stop saves the session; user may discard without saving. Duration is timestamp-derived; on app kill/resume, elapsed is recomputed from the start timestamp (INV-5). **`accumulatedSeconds` write timing (E5):** `accumulatedSeconds` is a denormalized cache written ONLY on stop (computed from `endedAt − startedAt`); while a session is running it is **nil / ignored** and is NEVER the source of truth. The live stopwatch display and ALL aggregation (Summary chart, KPIs, midnight-split per ADR-032) always derive from the `startedAt`/`endedAt` timestamps, never from the `accumulatedSeconds` cache. *Rationale: user decision; no countdown → no end-alert → no notification permission; timestamps are the single source of truth so a stale cache can never corrupt a total.*
- **ADR-015 — The quote library starts EMPTY; no bundled content, no seed (owner decision, supersedes the former builtin-library decision).** There is no built-in quote library and nothing is pre-installed. On a fresh store the `Quote` table is empty; the library grows only via manual entry (ADR-009/-010) and api-likes. The first-run/empty state (ADR-033, ADR-034) applies until the user adds content. *Rationale: owner decision — no bundled/seeded content.*
- **ADR-016 — First-release non-goals** (explicitly not built): account/login, iCloud sync, multi-user/social/share, Widget, Apple Watch, data export, paid/subscription, notifications, deep links, completion rate, streak, timer-bound-to-MIT. *Rationale: keep first release pure-local and focused.*
- **ADR-026 — A manual quote refresh persists as the day's chosen quote (per-scope).** Extends ADR-025. When the user refreshes, the chosen quote is written to a `DailySelectedQuote` record keyed by **(day, scope)** (T2), so closing and reopening the app the SAME day in the SAME scope shows the refreshed quote (not the original deterministic pick). The override is **scoped**: refreshing under `online` does NOT carry into `mine` — each scope has its own persisted pick for the day. **Online quotes stay TRANSIENT — a refresh does NOT populate the library.** An online (ZenQuotes) quote chosen by refresh (fetched via **`/random`**, ADR-012/ADR-025) is NOT persisted as a `Quote` row. Resolution (b): `DailySelectedQuote` stores the online quote's identifying value **inline** for display — its `text`, `author`, and `dedupKey` — so `quoteRef` does NOT point at a persisted library row for a transient online pick (for a LOCAL `mine` pick, `quoteRef` references the existing persisted `Quote`; see T2 `quoteRef` semantics). A refresh-persisted override therefore survives a same-day reopen WITHOUT the quote entering the library: it does **NOT** set `likedAt` on anything and does **NOT** make the quote appear in `mine`/Library. Only a user ♡ like (ADR-010) ever creates a persisted api row. It does not affect tomorrow's pick (tomorrow reverts to the deterministic pick, ADR-011, for that (day, scope) unless refreshed again). **Day-boundary revert & stale records:** the today-quote resolution queries `DailySelectedQuote WHERE day == today AND scope == active`. Stale records (`day < today`) are **INERT** (never read) and are NOT required to be pruned — they are unbounded but harmless, mirroring the lazy model of ADR-005. **Dangling `quoteRef` (C3):** if today's `DailySelectedQuote` override has a `quoteRef` (a `mine` local pick) whose referenced `Quote` row has been hard-deleted the SAME day, the today-quote resolution treats the override as **ABSENT** and falls through to the deterministic pick (ADR-011) — it NEVER dereferences a dangling ref or crashes. (A transient online override has `quoteRef == nil` and stores its content inline, so it cannot dangle.) *Rationale: user decision — a manual override should survive an app reopen within the day, must not leak across scopes, must not leak an online quote into the library, and must degrade gracefully if its target row is deleted.*
- **ADR-027 — Refresh is disabled on a degenerate FULLY-LOCAL pool only.** Extends ADR-025. The ≤1-quote disable rule applies ONLY to the **`mine`** scope — when its local `mine` pool has ≤1 quote (e.g. only the current quote): then the ↻ refresh control is DISABLED (greyed out, not tappable), re-enabling when the pool grows to ≥2 selectable quotes. **The `online` scope is NEVER disabled by pool size** — there is always a potential "different" online quote to fetch via `/random` (ADR-025); its failure behaviour is governed by ADR-013 instead (`online` → error + retry), not by disabling the control. *Rationale: user decision — pool-size disabling only makes sense when the pool is finite and local.*
- **ADR-028 — DELETED (moot; no builtin).** ~~Builtin quotes are likeable via flag-flip.~~ Removed by the owner decision that there is NO built-in quote library. The dedup-on-like behaviour it described (liking a quote whose `dedupKey` matches an existing row flips `likedAt` on that row instead of inserting a duplicate) survives generically in ADR-010/INV-4; the `mine` pool predicate it defined now lives in ADR-011. Nothing references a builtin flag-flip anymore. *Number retained, not reused.*
- **ADR-029 — Soft-delete stops rollover.** Resolves the ADR-005 × ADR-008 intersection. A soft-deleted MIT STOPS rolling: `isDeleted == true` gates the rollover query, so a deleted open MIT never advances `appearsOn` again and never reappears in any today list. *Enforces INV-6 across rollover. Rationale: user decision — a deleted task must not resurrect via the daily roll.*
- **ADR-030 — Cross-midnight undo of a soft-delete restores into today.** Extends ADR-008. If a soft-delete's undo is triggered after the calendar day has rolled, the restored (still-open) MIT is restored INTO TODAY (re-enters rollover as today's), never into the now-locked previous day — so it does not violate ADR-004/INV-3. **Field semantics on restore:** `createdOn` is PRESERVED (unchanged from the original) — only `appearsOn` is set to today and `isDeleted` is cleared; `deletedAt` is cleared. Preserving `createdOn` keeps the lifecycle timeline (ADR-007) honest about the MIT's true origin and its delete-gap. *Rationale: user decision — the previous day is read-only; the restored open task belongs to today, but its birth date is not rewritten.*
- **ADR-031 — The Summary average-mood KPI excludes missing days.** Extends ADR-023. The average-mood KPI is the mean over days that HAVE a `DailyFeeling` entry only; days with no feeling are EXCLUDED (not counted as 0). The mood/stress trend chart shows a gap/break for missing days. *Rationale: user decision — a missing entry is "no data", not a mood of zero.*
- **ADR-032 — A focus session spanning midnight is split at the midnight boundary.** Extends ADR-014/ADR-017. **WHERE the split lives:** the `FocusSession` is stored as ONE record (one `startedAt`/`endedAt`, duration timestamp-derived per ADR-014/INV-5) — it is NOT split at storage. The midnight split is a **read-model / query-time operation** performed ONLY for the Summary per-day focus aggregation (chart/KPI): each portion of the interval that falls within a calendar day is attributed to that day (the day join in ADR-017 is applied per-portion). **Multi-midnight:** a session crossing MULTIPLE day boundaries (e.g. >24h, or left running then stopped days later) is split at EACH calendar-day boundary it crosses; every day the interval overlaps receives exactly the portion of the interval within it (and the portions sum to the total duration). A currently-running (un-stopped) session is NOT counted in any day's total — only saved/stopped sessions count. **Running-session exclusion is an AGGREGATION rule only:** the "running (un-stopped) session excluded from day totals" rule applies to the STORED/AGGREGATED per-day totals (Summary chart + KPI) ONLY. The **live Timer stopwatch display** always shows total elapsed = `now − startedAt` per ADR-014 — a single undivided running number — including across midnight (a >24h running session shows continuous elapsed, NOT day-split). **The Timer screen presents NO summed "today total" at all (E3):** it shows only the live stopwatch plus the list of today's saved sessions (as WHOLE records) — NO summed per-day focus figure (that lives on Summary, ADR-017). Because the Timer never displays a day sum, the whole-record-vs-split divergence (below) never surfaces on the Timer as a contradiction. A running session contributes nothing to Summary/KPI day totals until stopped. **Divergence from T9 (intentional):** the Timer "today's sessions" list (T9) shows WHOLE, unsplit records attributed to a single day by `startedAt`'s calendar day, whereas Summary attributes split portions per day. These two views are **consistent-by-design** (whole-record vs split), not contradictory. *Rationale: user decision — per-day focus totals must be correct across midnight, without mutating the stored record.*
- **ADR-033 — Every screen has a purposeful empty/first-run state under both themes (intent fixed, exact copy left to build).** Each screen MUST render a deliberate empty state (not a blank view) in BOTH themes (ADR-022). Intent per screen: **Today** — the dashed intention placeholder row (ADR-024) plus a gentle first-run line inviting the user to set today's most important thing; and, for the quote area, when the active scope is `mine` and the `mine` pool is EMPTY, a **guiding empty state** ("Your library is empty — write one, or switch to Online to discover", ADR-034) — not an error, not a blank view; **Library** — an invitation to save a quote the user likes (e.g. "Your library is empty — save a quote you like"); **Timer** — a "no sessions yet today" line above the start control; **Summary** — charts still render their axes/frame with a "nothing to show yet" state rather than disappearing. Exact wording and per-theme dressing are left to the build; the REQUIREMENT is that each screen has a purposeful, themed empty state. *Rationale: user decision — emptiness should feel intentional, not broken; only existence was previously gated, so the intent is pinned here while copy stays flexible.*
- **ADR-034 — First-run default scope is `online`; empty-library behaviour is scope-dependent (owner decisions).** Because the library starts EMPTY (ADR-015), first-run behaviour must be pinned. **Default `TodayScope` on first run = `online`** (a new user's `mine` library is empty, so defaulting to `online` shows a quote immediately). **Empty library + `online` scope:** there is no local content, so today's quote is FETCHED from ZenQuotes (`/today`, ADR-012/-013). *With network:* a quote is shown. *Offline:* follow ADR-013 — `online` shows error + retry (there is nothing local to fall back to). **The fetched online quote is TRANSIENT — it does NOT create a `Quote` row (ADR-013 transient cache / ADR-026).** So on a fresh store, after a successful first-run online fetch, the `Quote` table STILL has ZERO rows and `mine`/Library remain EMPTY. A `Quote` row appears ONLY once the user ♡ likes the quote (ADR-010) — at which point a row is created with `source == api, likedAt == <now>` — or writes/adds a quote of their own. **Empty library + `mine` scope:** `mine`'s pool is empty → `pick()` returns nil → the screen shows a **guiding empty state** ("Your library is empty — write one, or switch to Online to discover"), NOT an error and NOT a blank view (ADR-033 Today empty-state intent). No fetch is performed (`mine` never fetches). Note this interacts with ADR-027: `mine` with 0-1 local quotes is a degenerate local pool, so refresh (↻) is disabled there. *Rationale: owner decisions — with no seed the app must behave sensibly from an empty library, and the default scope must be `online` so a brand-new user still sees a quote immediately.*
- **ADR-035 — Quote deletion is a HARD delete; un-like collapses to delete for api rows only (owner decision, refined by ADR-039).** Any quote in the library — user-authored or api-liked — can be **explicitly deleted**, which REMOVES the row entirely from the DB. For an **api-liked** quote, **"delete" and "un-like/un-save" are THE SAME action** (both remove the row). For a **user-authored** quote, an **explicit delete** removes the row, but **un-liking (clearing `likedAt`) does NOT remove it** — see ADR-039: a user row persists with `likedAt = nil` because `source == user` keeps it in the `mine` pool. So the "retain with `likedAt = nil`" state exists for user rows ONLY (never for api rows). There is **NO** separate soft-delete/trash for quotes (unlike MIT's ADR-008). **Dedup/resurrection consequence:** if a later api-fetch produces the same `dedupKey` as a previously-deleted quote, it is simply a fresh TRANSIENT online quote again (ADR-013/-026) — it is NOT resurrected as liked; it becomes a persisted row only if the user ♡ likes it again. *Rationale: owner decision — an api quote has no history-integrity requirement so delete/un-like collapse to one hard-delete action; a user-authored quote IS the user's content, so un-liking must not destroy it.*
- **ADR-036 — The theme token contract is a frozen public interface (T1 owns it).** Both themes (Ledger, Day Arc, ADR-022) MUST supply EVERY named token below; screens read tokens **by role** from the SwiftUI `Environment` and NEVER hard-code a color or font. T1 freezes this contract before any UI task builds. **Color roles:** `background`, `surface`, `surfaceRaised`, `textPrimary`, `textSecondary`, `textMuted`, `accent`, `accentCarried` (the ledger-red / rolled-over "carried" color), `divider`, plus a **Day-Arc gradient-anchor set** (`gradientTop`, `gradientMid`, `gradientBottom` — the per-screen gradient anchors the Day Arc theme selects via `screenRole`, ADR-037; Ledger supplies flat/neutral values for these so the token set is total in both themes). **Type roles:** `display`, `title`, `body`, `mono`, `eyebrow`. A screen that reads an UNDEFINED token (a role not in this set) is a build/contract error, not a silent fallback. *Rationale: freeze one public token vocabulary so screens are authored once and themed twice without hard-coded styling.*
- **ADR-037a (fix) — `themed(_:role:)` takes the screen role EXPLICITLY (per-screen gradients).** The role MUST be passed into token resolution, not read from `@Environment(\.screenRole)` at the same modifier site: an environment value injected by `.screenRole(_:)` flows only to *children*, so a sibling `.themed(_:)` reading it resolves the PARENT's default (`.today`) — the original chain `.screenRole(x).themed(t)` made every screen share the `.today` gradient. Fixed by `themed(_ theme:role:)` which injects both the resolved tokens AND the role. So the per-screen Day Arc gradients (Today dawn / Timer midday / Summary dusk) render correctly. *Rationale: field-fixed bug.*
- **ADR-037b (owner decision) — the nav bar is a FIXED light-grey capsule with dark icons and a darker selected-pill; identical in EVERY background, theme, and system light/dark mode.** iOS 26's SwiftUI `TabView` renders a floating glass capsule that **ignores `UITabBarAppearance`** (the opaque-white appearance we first tried had no effect — the glass bar let each screen's gradient show through, so it looked light on Timer and dark on Today). Fixed by NOT using the system bar: `RootTabView` drives screen selection with a `Tab` enum and draws its **own** fixed capsule at the bottom — light-grey ground (`white 0.93`), unselected icons `white 0.45`, selected icons `white 0.10` on a darker pill (`white 0.82`). These are constant colors, not theme/dark-mode driven, so the bar reads identically over any screen background. **Motion:** switching tabs animates via a body-level `.animation(.spring, value: selection)` — the selected pill SLIDES between tabs (`matchedGeometryEffect`) and the screen cross-fades (`.id(selection)` + `.transition(.opacity)`); both are suppressed under Reduce Motion (`accessibilityReduceMotion`). *Rationale: owner decision — one stable, always-legible capsule nav (the system floating bar couldn't be pinned so we own it), with a gentle slide/fade so tab switches don't feel abrupt.*
- **ADR-037c (owner decision — REVISES ADR-037/-037a) — Day Arc's gradient tracks the REAL time of day and is the SAME on every screen.** The background is no longer chosen by `screenRole` (which gave each page a fixed time-of-day colour); instead every page shows one shared gradient = "the colour of the sky right now", interpolated continuously across the day from four keyframes (dawn 06:00 → midday 13:00 → dusk 19:00 → night 23:00, wrapping across midnight back to dawn). Resolution takes a fractional hour from the injectable `Clock` (ADR-038): `ThemePalette.tokens(for:atHour:)`; `DayArcPalette` interpolates its gradient anchors by the hour and ignores the role for the background; Ledger ignores the hour entirely. Switching tabs no longer changes the background. *Rationale: owner decision — "日弧" should reflect the real day, not which page you're on; a single sky colour that drifts through the day is truer to the concept.* (Known limitation: within one foreground session the colour is computed at render/tab-switch/relaunch, not on a live per-minute timer — it refreshes whenever the view re-renders; a live ticking drift is a possible future enhancement.)
- **ADR-037d (owner decision) — text AND the nav bar adapt to the time-driven background's brightness.** Because the Day Arc background now drifts from bright daytime blues to deep night (ADR-037c), fixed light text would wash out at midday and a fixed light nav capsule would clash. `ThemeTokens` gains `isLightBackground` (from the gradient's top+mid relative luminance, Rec. 709, threshold 0.42). **Text:** Day Arc picks dark text over a light background and light text over a dark one (`textPrimary/Secondary/Muted` swap); Ledger is always light-paper → dark ink. The dark (daytime) `secondary`/`muted` tones are kept fairly deep (≈0.18–0.28 grey) rather than pale, so eyebrows/captions/placeholders stay legible on the mid-brightness daytime sky. **Nav bar (revises ADR-037b's fixed capsule):** the capsule is now the current gradient-mid tone as translucent glass, and its icons adapt via `isLightBackground` (dark icons + dark selected-pill over a light bar, light over a dark bar) — so the nav tracks the day like the rest of the app while staying legible. *Rationale: owner decision — once the background moves through the day, both type and chrome must follow its brightness to stay readable.*
- **ADR-037e (owner decision) — the amber accent is retired; accent splits into three role-based tokens.** The single amber `accent` looked wrong and, as a flat color, either clashed or (as flat white) vanished on the bright daytime sky. Split into: **`accentFill`** — a near-white fill for solid buttons & selected chips (their label stays the dark `background`, so white-on-white can't happen); **`accentOnBackground`** — an adaptive ink (dark on a light background, light on a dark one via `isLightBackground`, ADR-037d) for glyphs, tinted labels, and CHART marks painted on the sky (never flat white, which disappears at midday); **`likedAccent`** — a saturated hue kept for the "liked/favorited" heart so that state still reads at a glance. Every `colors.accent` call site was reclassified: filled buttons/selected fills → `accentFill`; icons/charts/tinted text → `accentOnBackground`; the like heart → `likedAccent`. Ledger maps all three to its ledger-red. *Rationale: owner decision — no more yellow; white where it's safe (fills with dark labels), adaptive where it's painted on the moving sky, and a real hue where "liked" must stay legible as a state.*
- **ADR-037 — Day Arc per-screen gradient is driven by a `screenRole` Environment value.** T1/ADR-022 add a `screenRole` `Environment` value with cases `{ .today, .timer, .library, .summary }`. Each screen SETS its `screenRole`. The **Day Arc** theme CONSUMES it to select its per-screen gradient anchors (dawn on Today, midday on Timer, dusk on Summary, etc., ADR-022) from the ADR-036 gradient-anchor tokens; the **Ledger** theme IGNORES `screenRole` (its neutrals are screen-independent). This resolves the "per-screen gradient vs theme-agnostic screen" contradiction: the screen stays theme-agnostic (it only declares its role), and the theme decides whether the role matters. *Rationale: keep screens theme-agnostic while letting Day Arc vary by screen; a single declared role drives the gradient, not per-screen theme branches in the screen code.*
- **ADR-038 — Canonical day key (S1).** Every `day` / `*On` calendar-day field (MIT `createdOn`/`completedOn`/`appearsOn`, `DailyFeeling.day`, `DailySelectedQuote.day`) and EVERY by-day aggregation/join uses the LOCAL `startOfDay` `Date` computed via the injectable `Clock`'s calendar. There is ONE canonical day representation across the whole app; all day-joins (MIT ⋈ DailyFeeling ⋈ FocusSession-portion ⋈ DailySelectedQuote) compare this same value. *Rationale: a single day representation prevents off-by-one/timezone drift across aggregations; the injectable `Clock` keeps it testable.*
- **ADR-039 — Un-liking a user-authored quote clears the like but RETAINS the row (owner decision, carve-out to ADR-035/INV-9).** Refines the "un-like == hard-delete" rule of ADR-010/ADR-035/INV-9 to be `source`-dependent: for a **`source == api`** row, clearing `likedAt` (un-like) removes the row (same as delete). For a **`source == user`** row, clearing `likedAt` (un-like) does **NOT** remove the row — the row IS the user's authored content and remains in the `mine` pool via the `source == user` predicate (ADR-011); it is removed ONLY by an explicit "delete my quote" action. This carve-out does NOT contradict the api-row hard-delete rule; the "retain with `likedAt = nil`" state exists for user rows only. *Rationale: owner decision — un-liking must never destroy user-authored content, whereas an api-liked row has no independent existence and is correctly removed on un-like.*
- **ADR-040 — The persisted current `TodayScope` selection is owned by T1's settings layer (S6).** The user's currently-selected `TodayScope` (persisted, defaulting to `online` on first run per ADR-034) lives in T1's settings layer alongside the persisted `Theme` selection — a SINGLE source of truth. **T5** (quote service) READS it to resolve today's pick; **the Settings screen (ADR-046) WRITES it** (revised — the writer moved from the Library picker to the dedicated Settings screen). No other component persists a scope. *Rationale: one owner for the persisted scope prevents divergent copies between the reader (T5) and the writer.*
- **ADR-046b — The evening feeling is a two-step entry: a small state card on Today + a full-screen sheet (owner decision, revises ADR-019's inline block).** The old inline block (two rows of six 0–5 circles + a why box + a full-width Save) was too tall/heavy for Today. Split it, mirroring the MIT intention ritual (ADR-024): **Today shows a small card** — an EMPTY heart + "Tap to log how today felt" when nothing is logged, a FILLED heart + "Mood M · Stress S" summary once logged; tapping opens a **full-screen `FeelingSheetView`** with two 0–5 **sliders** (mood, stress) + a live value, an optional why, and Save. Same data + rules as before (one-per-day upsert INV-7, same-day editable / cross-day read-only INV-8). *Rationale: owner decision — shrink Today's footprint and make logging a focused full-screen step, consistent with how an MIT is set.*
- **ADR-046 — A dedicated Settings tab is the single place to change the visual Theme and the quote Source (owner decision).** A 5th bottom tab, **Settings** (gearshape icon, `screenRole == .settings`, ADR-037), hosts two controls: a **Theme** segmented picker (Ledger / Day Arc, ADR-022) and a **Today's Quote Source** segmented picker (`TodayScope` mine / online, ADR-040). Both write straight to `AppSettings` (the single persisted source of truth): writing `theme` also mirrors to the widget (ADR-044); writing `todayScope` re-points T5's next daily pick. **The Library screen no longer hosts a source picker** — source selection is consolidated here so there is exactly one place to change theme + source. The screen is theme-agnostic (reads tokens by role, ADR-036) and has NO business logic beyond binding to `AppSettings`. *Rationale: owner decision — give theme (previously changeable only programmatically) and source a discoverable home; one settings surface instead of a source picker buried in Library.*
- **ADR-041 — Widget families & content: a medium Home Screen widget and a combined Lock Screen widget (promotes the former OQ-06 "Widget" into first release).** Reconcile ships a WidgetKit extension (T12) with **exactly two widget families**: (1) a **Home Screen widget — `.systemMedium` only** (one wide widget) showing the **stopwatch figure AND the quote side by side**; (2) a **Lock Screen widget — one combined `.accessoryRectangular`** showing **BOTH the stopwatch figure and the quote**, with the quote **truncated/short** to fit the tiny lock-screen space. No other widget sizes/families in first release (no small/large home widget, no separate lock-screen quote-only or timer-only widget). **Layout — TWO states (owner decision):** the widget has two distinct layouts driven by whether a `FocusSession` is currently running:
  - **RUNNING** → `time │ quote — author`: a divider (a vertical hairline on the medium home widget; a separator on lock), the **live self-advancing time on the left** (`Text(startedAt, style: .timer)`), the **quote on the right** with its **author in small caps beneath**.
  - **IDLE (nothing timing)** → the **quote fills the ENTIRE widget** (set larger), with author beneath — **NO time figure, NO divider**. There is **NO** accumulated-time display when idle; the running figure simply disappears and the quote takes the whole surface. (This supersedes any earlier "idle shows today's accumulated focus" wording.)
  Both layouts render EXACTLY those elements and NOTHING else — NO field labels ("Focus"/"Today's focus"), NO running/paused word or status dot, NO app/brand mark. The running-vs-idle distinction is carried by the layout itself (time present = running; quote-only = idle), never by a label. **Quote content:** the SAME quote the app shows as **today's quote**, consistent with the app's current `TodayScope {mine, online}` selection (ADR-011/ADR-040) and any manual refresh override (ADR-025/ADR-026) — the widget mirrors the app's resolved today's-quote value, it does NOT re-derive or re-pick. On the Lock Screen the quote is truncated. *Rationale: owner decision — promote Widget to first release as one wide home widget + one combined lock-screen widget, each surfacing the day's focus figure and today's quote.*
- **ADR-042 — Widget reads an App Group shared snapshot; the app is the single writer; the widget is read-only.** The widget extension reads app data ONLY via an **App Group shared container** (shared UserDefaults / a small shared snapshot file / a shared store) — it runs **no business logic and no network calls** of its own. The **app** writes the widget-relevant **snapshot** into the shared container **whenever the relevant state changes**: (a) on **focus session start/stop/discard** (writing the running-session `startedAt`, or clearing it and writing today's accumulated seconds), and (b) on **quote pick/refresh/scope change** (writing today's-quote `text` + `author`), and (c) on **theme change** (writing the persisted `Theme`, ADR-044). The snapshot is a **read-only projection** (§2) — the app's SwiftData store stays authoritative. **The widget NEVER mutates app data:** it exposes no start/stop/like/refresh path and no write-back to the shared container in first release (controlling the timer from the widget is deferred — OQ-08). *Rationale: owner decision — keep all business logic and networking in the app, hand the widget a pre-computed read-only snapshot through an App Group, single-writer to avoid divergence.*
- **ADR-043 — Widget timeline refresh: self-advancing timer text for a running session, periodic reload for state/day flips, no per-second tick, no widget-side network.** The widget uses a `TimelineProvider` that reads the ADR-042 shared snapshot. WidgetKit **cannot tick every second on its own**, so the **running** stopwatch figure is rendered as a **system self-advancing `Text(startedAt, style: .timer)`** driven by `startedAt` — it advances without per-minute reloads. The provider **still schedules periodic reloads** to (a) **flip "running" → "accumulated"** when a session ends (and vice-versa) and (b) **pick up a new day's quote / reset the accumulated figure at local midnight**. The provider performs **no network fetch** — a stale snapshot is refreshed by the app's next write, not by the widget calling ZenQuotes. *Rationale: owner decision — lean on the system timer text for the live figure, use timeline reloads only for the coarse state/day transitions the timer text cannot express, and never let the widget do I/O.*
- **ADR-044 — Widget theming: the Home widget follows the persisted `Theme`; the Lock Screen widget is system-tinted, theme-neutral.** The **`.systemMedium` Home** widget reads the persisted **`Theme` (Ledger/Day Arc, ADR-022/ADR-040)** from the shared container and renders in that theme (respecting the token vocabulary spirit of ADR-036, within the widget's constrained surface). The **`.accessoryRectangular` Lock Screen** widget is **constrained by the OS rendering mode** (tinted/monochrome on the lock screen), so it uses a **theme-neutral, legible** treatment and does **NOT** attempt full Day-Arc gradients — legibility under system tint wins over theme fidelity. *Rationale: owner decision — honor the user's theme where the surface allows it (home), fall back to a neutral legible treatment where the OS tints for us (lock).*
- **ADR-045 — Widget empty/edge states.** The widget renders **purposeful placeholders, never a blank view** (mirrors ADR-033's intent for the app). **No quote yet** (e.g. scope=`mine` with an empty library, ADR-034): the widget shows a **gentle placeholder** ("Open Reconcile to set today's quote" / the app name) rather than blank. **No session running** (idle): there is no time figure at all — the quote fills the widget (ADR-041 idle layout), so there is no "0/no focus" figure to show. The only genuine empty case is **no quote yet** (handled above). These apply on BOTH families (home + lock, with the lock copy kept short). *Rationale: owner decision — an empty snapshot must read as intentional, not broken.*

## 5. Task DAG

Stages are ordered; tasks within a stage may run in parallel unless `depends_on` says otherwise.

### Stage 0 — Project foundation
- **T1 — Xcode project + SwiftData scaffold.** `depends_on: []`
  Create the SwiftUI iOS app project `Reconcile`, SwiftData `ModelContainer`, app entry, a bottom-tab shell (Today / Timer / Library / Summary / Settings — the Settings tab per ADR-046), a `Clock` abstraction (injectable "now"/"today" so rollover & date logic are testable), and the **theming layer** (ADR-022): a `Theme` enum {ledger, dayArc}, and the **frozen theme token contract (ADR-036)** — the named color roles (`background`, `surface`, `surfaceRaised`, `textPrimary`, `textSecondary`, `textMuted`, `accent`, `accentCarried`, `divider`, plus the Day-Arc gradient-anchor set `gradientTop`/`gradientMid`/`gradientBottom`) and type roles (`display`, `title`, `body`, `mono`, `eyebrow`) exposed **by role** via SwiftUI `Environment`, which **both** themes MUST fully supply. Also add the **`screenRole` Environment value** `{ .today, .timer, .library, .summary }` (ADR-037): each screen sets it; Day Arc consumes it to pick its per-screen gradient anchors, Ledger ignores it. **Settings layer (ADR-040):** persist BOTH the `Theme` selection AND the current `TodayScope` selection (default `online`, ADR-034) here as the single source of truth (T5 reads the scope, T8 writes it). Screens later read tokens from the environment (theme-agnostic) and never hard-code a color/font. No feature logic yet.

### Stage 1 — Domain models & core services
- **T2 — SwiftData models + invariants.** `depends_on: [T1]`
  Define `@Model` `MIT` (id, text, reason?, status, createdOn, completedOn?, appearsOn, isDeleted, deletedAt?), `Quote` (id, text, author?, source, `likedAt?` — *the SINGLE stored like field, source of truth; `liked` is a DERIVED/computed convenience property `liked ≡ likedAt != nil`, NOT a stored field — INV-9*, dedupKey — *computed by the pinned INV-4 formula `normalize(text)+"|"+normalizeAuthor(author)`*), `FocusSession` (id, startedAt, endedAt?, accumulatedSeconds — *duration is ALWAYS derived from `startedAt`/`endedAt` timestamps per INV-5/ADR-014; `accumulatedSeconds` is only a denormalized cache written ONLY on stop (from `endedAt − startedAt`), nil/ignored while running, never the source of truth — ADR-014*), `DailyFeeling` (id, day, mood 0-5, stress 0-5, whyText?), `DailySelectedQuote` (id, day, scope, quoteRef?, inlineText?, inlineAuthor?, inlineDedupKey?, isManualOverride) — *the per-day, PER-SCOPE selected-quote record keyed by **(day, scope)**, ADR-026; a refresh under one scope never carries into another. **`quoteRef` semantics (ADR-026):** for a LOCAL `mine` pick, `quoteRef` is a stable reference to the existing persisted `Quote` row (and if that row is hard-deleted same-day, the override is treated as ABSENT — dangling-ref fallthrough, ADR-026 C3). For a TRANSIENT ONLINE pick (refresh in the `online` scope), `quoteRef` is nil and the online quote is stored INLINE via `inlineText`/`inlineAuthor`/`inlineDedupKey` for same-day display — the online quote is NOT persisted as a `Quote` row and NEVER enters the library/`mine` (resolution (b))*. Encode `MITStatus`, `QuoteSource`, `TodayScope {mine, online}`. **Canonical day key (ADR-038):** every `day`/`*On` field (MIT `createdOn`/`completedOn`/`appearsOn`, `DailyFeeling.day`, `DailySelectedQuote.day`) and every by-day aggregation is the LOCAL `startOfDay` `Date` from the injectable `Clock`'s calendar — one canonical representation across all models and day-joins. Enforce INV-1/-4/-5/-6/-7/-9 at the model/service layer.
- **T3 — REMOVED (no seed; the library starts empty).** The former built-in quote seed task is deleted per the owner decision (ADR-015): there is no bundled content, nothing is seeded, and no downstream task depends on it (T5 now depends only on `[T2]`). *No gate.*

### Stage 2 — Features (parallelizable)
- **T4 — MIT service: create/edit/complete/rollover/soft-delete + daily-stat.** `depends_on: [T2]`
  Implement all MIT operations and the **lazy rollover** with the pinned **app-open ordering (ADR-005/D2): (1) rollover FIRST** — advance `appearsOn = today` for every MIT with `status == open AND !isDeleted AND appearsOn < today`; **(2) THEN** apply the cross-day read-only lock (INV-2/-3/ADR-004) only to records terminal or still historical after step 1 (so an open past-due MIT is advanced, not frozen). **Completion bookkeeping (ADR-004/D1):** complete sets `status=completed, completedOn=today`; flipping `completed→open` same-day sets `status=open` AND `completedOn=nil`. Daily stat = count of MITs whose `completedOn` is that day (ADR-006). Soft delete + undo (ADR-008).
- **T5 — Quote service: source selection, daily pick, like/persist/dedup, user entry, ZenQuotes fetch + degrade.** `depends_on: [T2]`
  Deterministic daily pick per `TodayScope {mine, online}` (read from T1's settings layer, ADR-040). **`mine`** = seeded by (day, scope) into a stably-sorted **local** pool (ADR-011); the local `pick()` returns `Quote?` (nil on empty pool → guiding empty state, no modulo-by-zero — the sole element on singleton). **`online`** = the ZenQuotes **`/today`** quote, picked directly (not indexed, ADR-011/-012); `mine` never fetches. Pick composition: `mine` = local index (empty→nil, singleton→that quote); `online` = `/today` (offline → error+retry, ADR-013). Default scope on first run = `online` (ADR-034). The library starts EMPTY (ADR-015) — no seed step. `mine` pool predicate = `source == user OR liked == true` (ADR-011). ZenQuotes fetch with ~10s timeout + **transient in-memory same-day cache** (ADR-012/-013) — a displayed/refreshed online quote is NEVER persisted as a `Quote` row. Like → persist the transient api quote (`source==api, likedAt=now`) + dedup by `normalize(text)+author` (ADR-010/INV-4); user entry goes straight into the library. **Un-like/delete is `source`-dependent (ADR-035/ADR-039/INV-9):** un-liking a `source==api` row HARD-deletes it (same action as delete); un-liking a `source==user` row clears `likedAt` but RETAINS the row (it stays in `mine` via `source==user`); an explicit "delete my quote" removes a user row; a subsequent identical api fetch is a fresh transient quote, not auto-re-liked. `online`+offline → surface an error state (ADR-013). Empty-library behaviour per ADR-034 (`online` fetches a TRANSIENT quote → `Quote` table stays at ZERO rows until a ♡ like; `mine` empty → guiding empty state, no fetch). **Manual `refresh()`** swaps within the active scope pool: `online` → fetch a DIFFERENT quote via **`/random`** (ADR-012/-025); `mine` → random different local quote (ADR-025); persists as the (day, scope) override (ADR-026) — a transient online override stores the quote inline (does NOT set `likedAt`, does NOT enter the library). Today-quote resolution treats a dangling `quoteRef` (target hard-deleted same-day) as ABSENT → falls to the deterministic pick (ADR-026 C3). Network layer behind a protocol so tests inject a fake.
- **T6 — FocusSession service: stopwatch start/stop/discard, timestamp-derived elapsed, multi-session.** `depends_on: [T2]`
  Start/stop/discard; elapsed recomputed from `startedAt` on resume (survives app kill) per ADR-014/INV-5. Multiple sessions/day.
- **T11 — DailyFeeling service: upsert today's diary (one-per-day), mood/stress + optional why, cross-day lock.** `depends_on: [T2]`

Reject edits to a cross-day historical entry (INV-8). ### Stage 4 — Widget extension
- **T12 — WidgetKit extension: medium Home widget + combined Lock widget, App Group shared snapshot + app-side writer, TimelineProvider (ADR-041–ADR-045).** `depends_on: [T1, T5, T6]`
